# feedback/ — 이전 실수와 피드백 (이 저장소의 목적)

## 역할
2026-11-05 사용자 결정으로 이 저장소의 목적은 **"이전의 실수들을 통해 발전해 나간다"**가 됐다(원안의 '추론 논리를 모아 비용을 아낀다'는 접음 — [docs/purpose-2026-11-05.md](../docs/purpose-2026-11-05.md)). 여기가 그 본체다.
- **실수** = 틀린 것만이 아니라 "그때로 돌아가면 그렇게 하지 않을 것" 전부. 사용자가 싫어하거나 좋아한 것, 비용·시간이 낭비된 것, 작업이 실패한 것. 결국 피드백이다.
- 에이전트는 **일하기 전에 읽고 들어간다.** 계산 엔진이 끼어드는 게 아니라 "읽고 조심하기"다. 다만 읽는 단계와 쓰는 단계는 검사가 막는다(아래 "강제").

## 두 층
| 자리 | 무엇 | 크기 |
|---|---|---|
| `main/<일>.md` | 그 일을 하면 **꼭 읽는** 메인 피드백. 행동 문장 하나 + 한 줄 이유 + 출처. `common.md`는 모든 일에 | 파일마다 **최대 10개** |
| `whitepaper.md` | **백서(자서전)**: 피드백 전부, 날짜·원 기록 링크·색인 낱말. 에이전트가 한 번 읽어 "이런 일이 있었지"를 알고, 행동 전에 색인에서 자기 일의 낱말을 찾아 걸리는 항목만 다시 본다 | 제한 없음 |

메인에 있는 항목도 백서에 다 있다(`자리: 메인 <파일>`). 백서는 날짜순 일기가 아니라 하는 일별 장이고, 새 항목은 끝 번호 다음으로 덧붙인다(글은 고치지 않고 `자리`만 바뀐다).

## 피드백 한 건의 모양 (코드가 읽는다 — `python -m feedback check`)
```
### F012 · 제목
- 색인: 낱말, 낱말            ← 아래 "색인 낱말"에서만
- 그때: 무엇을 했고 무엇이 됐나
- 다시 하면: 행동 문장 (다음에 바로 쓸 수 있게 — "조심하자"는 안 된다)
- 왜: 한 줄
- 출처: 사용자 / 실측 / AI 판단, 날짜, 원 기록(배치·기록 id·보고서)
- 자리: 메인 <파일> / 검사로 졸업 / 백서만
```
출처 무게: 사용자 > 실측 > AI 판단(루트 규칙과 같다). 메인 파일의 줄은 `- **F012** 행동 문장 — 이유. (출처, 날짜)`.

## 거름망 — 무엇이 피드백인가
1. **그때 알 수 있었던 것으로 다르게 할 수 있었나?** 아니면 피드백이 아니다(백서 끝 "거름망에서 뺀 것"). 결과만 나빴고 알 길이 없던 것(컨테이너 재시작, 연결 끊김, 보내기 전에 모르는 그림 수)을 올리면 쓸데없는 조심만 는다. 되풀이되어 **이제는 아는 것**은 환경 사실로 올린다.
2. 행동 문장이어야 한다. "이미지 조심"은 못 쓰고, "스토어 그림은 `=w1000` 주소로 받아 Read로 본다"는 쓴다.
3. 좋았던 것도 올린다 — "다음에도 한다"로(F014·F047).
4. agent_usage의 빗나감 기록(`review.wrong`·`why`)은 예측 조각을 고치는 좁은 피드백이라 여기 다 옮기지 않는다. 거기서 나온 **일반 교훈**만 올린다.

## 메인에 올리는 기준 (파일마다 ≤10, 넘으면 하나를 내린다)
- 되풀이된 것(두 번 걸리면 올린다) · 대가가 컸던 것(시간, 되돌리기, 사용자 신뢰) · 자주 마주치는 상황 · **사용자가 직접 준 피드백은 한 번이라도**.
- **졸업**: 메인 피드백이 검사·도구로 막히게 되면 메인에서 내리고 백서의 `자리`를 "검사로 졸업"으로. 그래서 메인에는 아직 자동으로 못 막는 것만 남는다(F051: 문서에만 적힌 단계 4/53, 검사가 막는 단계 72/73).
- 나아지고 있는지는 **재발**로 잰다: 피드백이 있었는데 같은 일이 또 났으면 그 항목에 "재발 YYYY-MM-DD"를 붙이고 "안 읽혔나 / 읽었는데 문장이 흐렸나"를 가른다.

## 색인 낱말 (여기서만 고른다 — 같은 뜻은 같은 낱말)
API, PDF, git, 검토, 게임, 고증, 공개저장소, 그림, 글꼴, 기록, 네트워크, 논리집, 데이터, 렌더, 맥락, 멈춤, 메인, 모델, 문서, 배치, 번호, 병렬, 보고서, 봉인, 브랜치, 사용자의도, 손글씨, 수업정리, 스토리, 시험, 앱, 예측, 웹차단, 이어보내기, 전송조건, 조사, 지시서, 클라우드세션, 토큰, 팀, 파일, 풀이지, 환경
- 새 낱말이 필요하면 이 목록에 더한다(검사가 목록 밖 낱말을 막는다). 분야·앱 이름은 색인 낱말로 쓰지 않는다 — 같은 교훈이 다른 분야에서도 걸리게(게임·풀이지·수업정리는 '하는 일'로 둔다).
- 메인 파일의 `키워드:` 줄은 색인과 별개로, 일의 설명(지시서·task 문장)에서 그 파일을 찾아 주는 낱말이다(`python -m feedback topics "<일 설명>"`). 2026-11-07부터 메인은 전부 읽으므로 키워드는 참고로만 쓴다(고르기가 거칠다, F102).

## 명령 (저장소 루트)
- `python -m feedback check` — 백서·메인 모양 검사: 칸 여섯, 색인 낱말, 번호 중복·순서, 메인 ≤10·`키워드:`·`읽는 때:` 줄·`common.md`, 메인 줄의 번호가 백서에 있고 `자리`가 맞는가(거꾸로도), 색인 표가 최신인가. 문제가 있으면 종료 코드 1. **테스트가 같이 돈다**(`tests/test_feedback.py`).
- `python -m feedback index --write` — 백서의 색인 표(낱말 → 항목)를 다시 만든다. 항목을 더하면 돌린다. `--write` 없이는 표를 보여 주기만 한다.
- `python -m feedback topics "<일 설명>"` — 키워드가 글에 들어 있는 메인 파일 목록(대소문자 무시 부분 문자열, `common`은 늘) — **참고용**. 보낼 일 파일에 붙일 `[feedback] read` 줄은 메인 파일 전부로 찍는다(2026-11-07부터 그게 규칙).
- `python -m feedback find <낱말>...` — 색인 낱말로 백서 항목 찾기(에이전트의 "주의할 점이 있었나?"). 보낼 일 파일에 붙일 `searched = [...]` 줄도 찍는다.
- `python -m feedback labels [--out 경로] [--brief-root 저장소=폴더 ...]` — 피드백 찾기의 정답: `feedback.hit` 칸이 있는 보낸 기록·직접 한 일마다 한 줄 JSON `{id, kind(dispatch|direct), project, date, task, read, searched, hit, missed, brief}`(missed는 '없음: 이유'면 `[]`, 아직 안 적었으면 `null`; brief는 지시서 경로, 없으면 `null`). 기본 `out/feedback/labels.jsonl`(git 제외). 나중에 일 글(task + 지시서)을 임베딩해 이 정답을 찾아 오는지 볼 재료다(그 시험은 아직). `--brief-root gemmin=<그 저장소 폴더>`(여러 번 가능)를 주면 행마다 `brief_text`(지시서 글)를 붙인다 — 저장소 이름이 맞고 파일이 있으면 그 글, 없으면 `null`이고 몇 건인지 오류 출력에 한 줄. 옵션이 없으면 `brief_text` 칸 자체가 없다.

## 강제 (2026-11-06부터, `python -m domains.agent_usage.dispatches`와 테스트가 막는다 — batman 기록 제외, 코드는 `dispatches.feedback_send_errors`·`feedback_review_errors`)
- **읽기**: 보낼 일 파일에 `[feedback] read = ["common", "brief", …]`(읽은 메인 파일 이름). **2026-11-07부터는 메인 파일 전부**가 들어 있지 않으면 `record send`가 보내지 못한다(모두 합쳐 76항목·19KB쯤이라 싸다; 그 전 날짜 기록은 `topics(task)`가 고른 파일이 기준이었다). 기록에는 `[dispatch.feedback] read = […]`로 남고, 보낸 뒤 출력에 그 파일들의 경로와 F 줄(많으면 번호와 제목)이 찍힌다 — 지시서에 붙여 작업자도 읽게 한다.
- **정답 모으기** (2026-11-06 사용자 결정, 2026-11-07부터 필수): 나중에 피드백 찾기 모델(일 글을 임베딩해 걸릴 항목을 찾아 오기)을 시험할 정답을 쌓는다.
  - `[feedback] searched = ["낱말", …]` — 메인 모델이 이 일에 맞는 백서 색인 낱말을 **스스로 골라** `python -m feedback find`를 돌린 낱말(한 개 이상, 위 '색인 낱말' 목록 안). `record send`가 다시 찾아 항목(번호 · 제목 · 자리)을 찍는다 — 메인 모델의 맥락을 한 번 지나가게.
  - `[feedback] hit = ["F014", …]` — 읽은 메인과 찾은 백서 항목 중 **이번 일에 걸린다고 본 것**(백서에 있는 번호). 걸릴 게 없으면 `hit = []`와 `hit_none = "이유"`(5자 이상).
  - 끝나면 `review.missed` — 보낼 때 이미 있었는데 hit에 없던, **알고 보니 걸린** 기존 항목(예: 이번에 새로 올린 피드백을 막았을 기존 항목) 번호 목록 또는 `"없음: <이유>"`. `record finish … --missed "F014,F051"`. hit와 겹치거나 이번에 새로 올린 번호(review.feedback)면 막는다.
  - hit + missed = 그 일의 정답. `python -m feedback labels`가 뽑는다.
  - (선택, 아직 필수 아님) `brief = "<저장소>:<상대경로>.md"` — 보낼 일 파일·직접 할 일 파일의 맨 위 칸(`session`처럼). 작업자에게 준 지시서 글이 있는 곳(예: `"gemmin:docs/briefs/p246.md"`). **이 저장소는 공개라 지시서 글은 여기 저장하지 않는다** — 비공개 저장소(gemmin `docs/briefs/p###.md`)에 두고 기록에는 경로만. `record send`/`record direct`가 옮기고, 검사는 모양만 본다(저장소 이름 `[A-Za-z0-9_.-]`, 콜론, `/`로 시작하지 않고 `..`이 없는 `.md` 경로 — `feedback.brief_error`). 임베딩 시험은 `labels --brief-root`로 글을 붙여 `out/`(git 제외)에서만 읽는다.
- **쓰기**: 끝난 기록의 `review.feedback` — 이번 일에서 새로 올린 피드백 번호 목록(`["F102"]`, 백서에 있어야 함) 또는 `"없음: <이유>"`(한 줄, 이유 5자 이상). 비우면 검사가 막는다. `record finish … --feedback "F102,F103"`(또는 `--feedback "없음: 이유"`)가 적고, 안 주면 출력의 '남은 일'에 뜬다. 새 항목은 백서에 적고 `index --write`, 메인에 올리면 그 파일에도.
- 직접 한 일(`direct.toml`)도 같은 칸(`feedback.read`·`searched`·`hit`, `review.feedback`·`missed`).
- 다른 저장소 세션은 시작할 때 `main/common.md`와 자기 일의 메인 파일을 읽는다(루트 CLAUDE.md "다른 저장소 다루기").
