# domains/agent_usage/ — 하위 에이전트 시간·사용량 예측 (AI가 스스로 쌓는 논리집)

하위 에이전트를 보낼 때 걸릴 시간과 쓸 토큰을 예측해, 이유와 함께 사용자에게 말하기 위한 논리집. 2026-10-16에 만들었다.

## 역할 (사용자 결정 2026-10-16)
- **사용자는 이 분야를 판단하지 않는다**("잘 모르겠다"). 분야 A(AI 코딩 과정)를 보류한 것과 같은 이유다. 예외: 돌아보기에서 까닭을 못 찾은 빗나감('까닭 모름')만 사용자에게 넘긴다(2026-11-03 사용자 결정, 아래 고리 4).
- 대신 **AI가 사용자가 자기 논리집을 쌓는 방식을 그대로 따라 해서 스스로 쌓고, 스스로 쓴다.** 판정은 실측(`scripts/agent_usage.py`)이 한다.
- 사용자에게는 시간 구간(잠깐 ≤10분 / 다른 일 10–40분 / 신경 끄기 >40분)과 분·토큰 숫자, 그렇게 본 이유를 말한다(R_say_numbers_v3). 범위가 두 구간에 걸치면 범위의 가운데 값(√(하한×상한))이 든 구간으로 말한다(2026-11-03 사용자 결정 — 그 전에는 긴 쪽, v2).
- batman 지휘 모델이 이 논리집으로 예측한다(batman CLAUDE.md §7). batman AGENT-LOG의 에이전트별 예측 줄을 여기 기록으로 옮기고, 클라우드 세션이 push하지 못하면 batman STATUS에 "proviso sync pending: batch N"이 남는다(PC 세션이 옮긴다). 이 저장소의 하위 에이전트 기록은 `project = "proviso"`, id `p01`부터.

## 파일
- `knowledge.toml`: 목표 3, 상태, 관찰, 가설, 지휘 모델과 정리한 AI가 쓴 예측 규칙(버전별). 관찰 출처: `measured`(실측) / `director`(지휘 모델 메모) / `conversation`.
- `dispatches.toml`: 작업마다 **예측 → 실측 → 돌아보기** 한 묶음. 보낸 순서대로 이어 쓴다. 상황 값(대 보기)은 상태 id = 예/아니오/일부/모름. 칸 설명은 파일 맨 위 주석.
- `dispatches.py`: 기록 검사 + 예측·실측 비교표. `python -m domains.agent_usage.dispatches`. 시간은 예측 분 범위를 세 마디 구간으로 바꿔 채점하고(옛 S/M/L/XL 등급은 역사로만 남음), 걸친 예측이 어디에 떨어졌는지, 분이 빗나간 기록이 속도(턴은 맞음) 탓인지 양(턴도 틀림) 탓인지를 집계한다.
- `predict.py` (2026-10-19): **계산기**. `python -m domains.agent_usage.predict <기록 id | 상황 파일>` — 상황 값과 project만 보고 계산 조각(효과 칸이 있는 가설, knowledge.toml의 '계산 조각' 구역)을 조합해 턴·분·토큰 범위와 말할 구간을 낸다. 근거 → 조각 → 조합 → 숫자로 설명하고, 빼도 말할 구간·토큰 등급이 안 바뀌는 조각은 설명에서 뺀다(쓴 조각 목록에는 남김). 맞는 기준값이 없으면 '모름'. 보내기 전에 적은 빗댄 기록(`predicted.analog`)이 있으면 비유 계산을 따로 보여 준다. 상황 파일: `project = "..."`, `[situation]` 상태 = 값, (선택) `analog = "기록 id"`.
- `fit.py`: 조각의 **범위 숫자를 기록에서 기계적으로 맞춘다**(사람이 고르지 않음). 모양(무엇에·어떻게·언제·방향·이유)은 손으로, `python -m domains.agent_usage.fit final --write`가 seen_until까지의 기록으로 range·fit 칸을 다시 쓴다. 손으로 바꾼 범위는 audit 오류.
- `size.py` + `size.toml` (2026-11-03): 일의 크기 모델(정해진 일: 턴 = 기본 몫 + Σ 센 수 × 하나마다 몫) — 시험 중. `python -m domains.agent_usage.size`가 맞춘 몫과 미리 정한 시험을 보여 준다. 아래 "일의 크기 모델".
- `decide.py` + `decide.toml` (2026-11-03): 보낼까 판단 — 직접 할 때와 보낼 때의 토큰을 같은 단위로. `python -m domains.agent_usage.decide <상황 파일 | 기록 id>`. 아래 "보낼까 판단".
- `record.py` (2026-11-03): 묶음 명령 — `record send <보낼 일 파일>`(기록 덧붙이기 + 계산기 답 + 보낼까 판단 + 배치 머리 + 빗댄 기록 규칙), `record finish <id> <로그> [--after] [--report]`(실측·턴 표·보고서 경로), `record direct <파일>`과 `record finish <m001> <메인 기록> --after --until`(직접 한 일).
- `direct.toml` (2026-11-03): 메인이 직접 한 일(보낼까에서 '직접'을 고른 일) — 보낸 일과 같은 모양(판단 → 실측 → 돌아보기). 칸 설명은 파일 맨 위.
- `analog.py` + `analog.toml` (2026-11-03): 빗댄 기록 규칙(정해진 일은 가장 가까운 지난 일의 시간을 따른다) — v1 시험 실패, v2 시험 전(새 기록 30건). `python -m domains.agent_usage.analog [기록 id]`. 아래 "빗댄 기록 규칙".
- `holdout.py` + `holdout.toml`: 시간 순서 홀드아웃. 경계 d38b(앞 64건 / 뒤 61건, 뒤 절반의 끝은 p05로 고정 — 2026-10-22에 새 기록이 섞여 방향 성적이 흔들려서 고정했다. 그 뒤 기록은 checks.SEEN_UNTIL이 시험). `python -m domains.agent_usage.holdout` = 뒤 절반 성적(쪼개기 전 / 쪼갠 뒤 / 당시 손 예측)과 조각별 방향·크기 성적, `--gaps` = 앞 절반의 빈틈. holdout.toml의 세트는 앞 절반으로만 맞췄다(테스트가 확인).
- `history.md`: 지난 상태(배치별)와 지난 고리. 이 파일에는 지금 기준만 둔다(2026-11-02).
- `checks.py`: 가설과 규칙을 실측 기록으로 판정(`SOURCE = "measured"`). 규칙에는 주장 검사(가설과 같은 잣대)와 **쓴 예측 검사**(`used_minutes`·`used_turns`·`used_tokens`: 그 규칙을 `predicted.rules`에 적은, 보내기 전에 적은 예측이 실측과 맞았나)를 단다. 예측에 쓰는 살아 있는 규칙은 검사가 있거나 못 붙이는 까닭(`test_plan`)이 있어야 한다(테스트가 막는다). **가설은 세운 뒤에 나온 기록으로만 시험한다**(`SEEN_UNTIL`). 세울 때 본 기록은 "맞춰 본 것"으로 따로 보여 준다(사후 설명 방지). 빗댄 기록이 필요한 배수 가설은 `predicted.analog`(없으면 사후에 읽은 `PAST_ANALOG`, 보여 주기만)를 쓴다.

## 고리 (한 작업마다)
1. **보내기 전**
   - **보낼까부터** (2026-11-03): 도구를 대여섯 번 넘게 쓸 일이면 아래 "보낼까 판단"으로 정한다. 직접 하기로 했으면 `record direct`로 direct.toml에 남기고 끝나면 `record finish <m…>`.
   - **묶음 명령**: 보낼 일 파일(project·batch·task·agent·round·[situation]·[predicted] 손 예측)을 쓰고 `python -m domains.agent_usage.record send <파일>` 하나로 아래 기록 단계(덧붙이기·계산기 답·보낼까 판단·배치 머리·빗댄 기록 규칙)를 한다. 손으로 할 때는 아래 순서대로.
   - **기록을 먼저 덧붙이고 그 기록으로 계산기를 돌린다**: 상황 값은 가장 비슷한 지난 기록의 `[dispatch.situation]`을 복사해 바꾸면 쉽다. `python -m domains.agent_usage.predict <id>`로 근거를 보고 `--calc`로 나온 `[dispatch.calc]` 줄을 그대로 붙인다 — 상황 파일을 따로 만들면 값이 어긋난다(p138–p144의 계산기 답 '신경 끄기 45.6–91.2분'은 상황 파일에 S_resumed를 빠뜨린 값, 2026-11-03 확인; 지난 기록의 calc를 베끼지 않는다). 기록 전에 보고 싶으면 상황 파일로 `predict 상황.toml`. 말할 구간과 숫자, 쓴 조각을 본다. '모름'이면 아래 규칙 요약으로 손으로 잡는다. 계산기 답은 같든 다르든 늘 `[dispatch.calc]`(`told`, `minutes`)에 적는다 — 손 예측(`predicted.told`)과 어느 쪽이 나은지를 `dispatches` 출력의 '손 예측 vs 계산기'가 계속 센다(사용자 결정 2026-10-19).
   - 아래 "지금 쓰는 규칙 요약"에서 맞는 규칙을 고른다. 성적이 궁금하면 `python -m proviso check agent_usage`(규칙과 가설 모두의 성적표, 맨 끝에 한눈 표)를 본다(배치 19에서 규칙을 놓쳐 d42가 3배 빗나갔다).
   - R_preflight의 점검 넷을 한다(에이전트 id 대조, 지시문 말투, 도구 유무, 글 규칙).
   - `dispatches.toml`에 기록을 하나 덧붙인다: 상황 값(새 상태 S_fix_existing·S_open_seams·S_build_tools, 계산 조각이 쓰는 S_integration·S_many_turn_model 포함; S_small_codebase는 project로 정해진다), 예측(분 범위·등급·턴·토큰), 쓴 규칙 id(가설 id는 넣지 않는다 — 테스트가 실패한다), **빗댄 기록 id(`analog`)**, 이유, `written_before = true`(기본).
   - 기록에 `agent`(같은 에이전트 이름, 회차마다 같게)와 `round`(처음 = 1)를 적고, `python -m domains.agent_usage.analog <id>`로 규칙이 고른 지난 일을 본다(시험 중이라 참고, 동점이 여럿이면 규칙은 답하지 않는다).
   - 사용자에게 구간과 숫자와 이유를 말하고, 말한 구간을 `predicted.told`에 적는다(걸치면 가운데 값의 구간, `dispatches.say_zone`; 계산기도 같은 규칙). 옛 `time_class`는 더 적지 않는다. 찾을 것의 수를 모르는 작업은 "기본 몫 + 찾은 것마다 한 바퀴"로 나눠 말한다.
2. **도중 지시를 보내면** 그 기록의 `S_mid_notes`를 "예"로 둔다(H_mid_notes2가 이것으로 시험한다).
3. **끝나면 — 사용자에게 결과를 말하기 전에 기록부터** (컨테이너가 회수되면 대화 기록이 사라진다).
   - **묶음 명령**: `python -m domains.agent_usage.record finish <id> <로그> [--after <그 회차 시작>] [--report <경로>]`가 실측·턴 표·보고서 경로를 채우고 말한 구간이 맞았는지와 보낼까 판단을 견줘 보여 준다. 돌아보기 글과 배치 줄의 표·교훈만 손으로.
   - 실측: `python scripts/agent_usage.py <로그> --actual` → `[dispatch.actual]` 줄 그대로(분·턴·토큰 + 시작·끝 시각 `start`/`end`; 2026-11-04부터 시각이 없으면 오류, 못 재면 `time_skip = "이유"`). **이어 보낸 회차**는 한 로그에 앞 회차가 같이 쌓이므로 `--rounds`로 이 회차 시작 시각을 보고 `--actual --after <그 시각>`. 분은 완료 알림의 실행 시간이 있으면 그것을 쓴다(없으면 `--actual` 값). 멈춘 작업은 `status = "stopped"`, 끝났는지 모르면 `"unknown"`(판정에서 빠진다). 컨테이너 재시작으로 날아간 실행은 기록하지 않고 마지막 실행만 적는다(d51·d77; 보내기 전에 알 수 없는 바깥 상황이라 상태로 두지 않는다).
   - 턴 길이: 같은 로그에 `--turns --toml`을 돌려 나온 `[dispatch.turns]` 블록을 그 기록 끝에 그대로 붙인다(아래 "전제 1 시험"). 이어 보낸 회차는 `--rounds`로 본 그 회차 시작 시각을 `--after`에 줘서 그 회차만 잰다 — 로그가 한 파일에 쌓인 것은 skip 사유가 아니다(p138·p140·p141·p143·p144를 그렇게 뺐다; 2026-11-04부터 이어 보낸 회차의 skip은 검사가 막는다). 잴 수 없으면(클라우드 세션은 대화 기록이 없다) `[dispatch.turns]` 아래 `skip = "이유"` 한 줄. 표를 이유 문장에 섞어 쓰지 않는다.
   - 보고서: 작업 보고서 경로를 `review.report`에 적는다(이 저장소면 `docs/worklog/...`, 다른 저장소면 `"저장소:경로"`). 보고서가 없으면 쓰게 하고 나서 적는다.
   - **턴 길이 표와 보고서 경로는 2026-11-03부터 끝난 기록에 필수다. 없으면 `dispatches`와 테스트가 오류를 낸다**(2026-11-02 사용자 결정. 까닭: 문서에만 적힌 단계는 빠졌다 — p65 이후 세션 안 하위 에이전트 53건 중 `--turns` 4건, 검사가 막는 `review.wrong`은 72/73).
4. **돌아보기**: `python -m domains.agent_usage.dispatches`, `python -m proviso check agent_usage`.
   - **시간 구간이 빗나갔으면(말한 구간 `told`와 실제 구간이 달라도) `review.wrong`(틀린 조각 id: 규칙·가설·상태)과 `review.why`(넷 중 하나: "조건 흐림" → 쪼갠다 / "이유 틀림" → 새 버전 / "바깥 상황" → 예외 / "까닭 모름" → 고치지 않고 쌓아 두고 사용자에게 넘긴다)를 반드시 적는다.** p04부터 적용(검증 오류). 어느 조각인지는 `dispatches` 출력의 갈래로 먼저 가른다: 턴 범위가 맞았으면 분당 턴(속도) 조각, 틀렸으면 턴 수(양) 조각.
   - **까닭 모름** (2026-11-03 사용자 결정): 빗나간 크기가 흔들림 폭 안이거나(2026-11-03에 잰 대략: 같은 지시서를 범위만 바꾼 묶음끼리 분 ×1.3, 같은 스위치 묶음끼리 ×1.8), 보내기 전에 알 수 있었던 까닭이 보이지 않으면 까닭을 지어 붙이지 않는다 — 칸이 셋뿐일 때는 흔들림에도 까닭을 붙이게 됐다(p09는 형식상 '조건 흐림'). 이때 `review.wrong`은 비워도 된다. 사용자에게 결과를 말할 때 그 기록의 숫자와 확인한 것을 같이 넘기고, 답은 `review.user`에 적는다(답으로 까닭이 보이면 셋 중 하나로 바꾼다). 답이 없는 기록은 `dispatches` 출력의 '사용자에게 넘길 것'에 뜬다. 같은 조각에서 같은 쪽으로 되풀이되면 빠진 조건을 찾는다. 반대로 흔들림 폭 밖이고 보내기 전에 알 수 있었던 까닭이 보이면 한 건이라도 고친다(아래 '한 건이라도 기본 논리가 틀린 게 보이면 고친다' 그대로).
   - 맞았든 틀렸든 이유를 `review.reason`에 적는다. 맞았을 때도 적는다(H_cancel처럼 맞았는데 이유가 틀린 경우를 잡으려고). 다른 기록을 가리킬 때는 이 파일의 id를 쓴다(batman 쪽 이름과 섞인 적이 있다).
   - 이유가 새 주장이면 가설로 세우고 `checks.py`에 검사와 `SEEN_UNTIL`(지금 마지막 기록 id)을 넣는다. **한 건이라도 기본 논리가 틀린 게 보이면 고친다**(사용자 결정 2026-10-19: 특수한 경우일 수 있다). 한 건짜리는 '근거 1건'으로 표시되고, 방향은 이유 문장이 정하고 크기는 다음 기록이 시험한다.
5. **고치기**: 아래 "따라 할 방식"대로.
   - 규칙을 고칠 때는 이전 버전을 지우지 않고 `status = "retired"` + `replaced_by`로 남긴다. 겹치는 규칙을 모을 때도 같다.

## 전제 1 시험 (2026-10-26, 사용자와 정리 중 — 결론 전)
논리집의 뼈대 "시간 = 턴 ÷ 분당 턴"에는 **턴이 서로 비슷한 크기라는 전제**가 깔려 있다. 그래야 턴 수가 양이고 분당 턴이 속도다. 그런데 기록에서 턴 하나의 길이를 역산하면 4초(p38 grep·sed 대조)부터 20초(p33–p37 450줄 새로 쓰기), 37초(d55 긴 추론)까지 열 배 가까이 다르다. 분당 턴 띠를 벗어난 기록(p38·p45·p47·p50·p54·p02·p59–p64, 모두 위쪽)은 턴이 빨리 돈 게 아니라 **턴이 작았다**. 같은 "구현·문서"라는 모양 안에서도 그렇다.
- 턴 크기는 세 몫의 합이다: 쓰는 양(출력 글자) + 생각하는 양(맥락 크기를 탄다) + 도구가 도는 시간. 셋 다 로그에서 잴 수 있으므로 **전제 1은 가설이 아니라 측정으로 치운다**(사용자 결정 2026-10-26: 동작별 시간을 재서 직접 해 보고 결론낸다). 재면 "분당 턴"은 조건이 아니라 지시서에서 읽은 동작 섞임으로 계산되는 값이 되고, 남는 불확실성은 양("각 동작을 몇 번 하나")으로 모인다.
- 도구: `python scripts/agent_usage.py <로그> --turns` — 턴마다 동작 종류(도구 이름, Bash는 명령 첫 낱말), 턴 길이, 도구 시간, 출력 글자, 그때 맥락을 숫자로 뽑아 동작별 중앙값 표와 맥락 크기별 턴 길이를 낸다. `--toml`이면 같은 숫자를 기록에 붙일 `[dispatch.turns]` 블록으로(동작마다 n 턴 수, sum_s 합한 턴 길이, 중앙값 turn_s·tool_s·out_chars·ctx_k). 명령 본문·글은 출력하지 않는다.
- 측정 현황 (2026-11-02): 재기로 한 뒤 세션 안 하위 에이전트 53건 중 4건만 쟀다(p105·p106·p124·p130 — 숫자는 `review.reason` 문장 안). 절차가 문서에만 있어서 빠졌고, 2026-11-03부터는 `[dispatch.turns]`가 필수다. 지난 로그는 다시 재지 않는다(사용자 결정 2026-11-02). 4건에서 보인 것(결론 아님): 글 턴은 1.8–3초(맥락 20만이면 10초), 긴 턴은 도구 기다림(빌드·게임 실행 92초, npm 75초) — 턴 길이는 들쭉날쭉하지만 동작 종류로 갈린다.
- **재는 단위 확인** (2026-11-03, 이 세션 메인 대화 기록과 하위 에이전트 기록 p145 둘 다에서 확인 — p145: 28줄 = 응답 15개, 줄마다 같은 사용량, 줄마다 더한 토큰 3.16M · 응답마다 1.72M(×1.83), 생각 블록 9개 모두 0글자): 기록의 '턴'(`actual.turns`)은 응답 하나가 아니라 **블록 하나**다. 응답 하나가 생각·글·도구 호출마다 줄로 나뉘어 남는다(그 세션 36줄 = 응답 17개). 생각 블록은 0글자로 남아 생각하는 양은 글자로 못 잰다. `--turns`는 줄마다 '다음 줄까지 걸린 시간'을 붙여서 한 칸 밀린다 — 생각 줄에는 다음 블록을 쓰는 시간이, 도구 줄에는 도구 시간 + 다음 응답의 생각 시간이 붙는다. 같은 응답의 줄마다 사용량이 반복돼 줄마다 더한 토큰은 두 배쯤이다(4.34M, 응답마다 한 번 세면 2.10M). 지난 기록이 모두 같은 방식이라 기록끼리는 맞지만, 세 몫을 줄마다 나눌 수는 없다. 응답 단위로 바꿀지(당분간 옛 셈과 새 셈을 같이 적는 안)는 사용자 결정 대기.

## 일의 크기 모델: 정해진 일과 찾는 일로 나눈다 (2026-11-03 사용자 결정 — 모델을 만들기 전에 적음)
만든 뒤에 까닭을 적으면 결과에 맞춘 사후 설명이 되므로, 까닭과 시험 방법을 먼저 적는다.
- **나누는 스위치**: "만들 것과 고칠 곳이 지시서에 목록으로 다 적혀 있나"(예 / 일부 / 아니오). 지시서를 본 사람이면 누구나 같은 답을 낼 사실로 묻는다 — 막연하게 물은 S_full_brief("지시서와 약속 문서가 완전하다")는 241건 중 240건이 '예'라 아무것도 가르지 못했다.
- **나눈 까닭**
  1. '정해졌다'는 '작다'가 아니다: 곱하기로 세운 C_turns_spec_fixed('설계 문서가 정해지면 턴이 준다')는 방향이 틀려 물렸다. 정해졌다는 건 크기를 셀 수 있다는 뜻이다 → 이 스위치는 곱하기가 아니라 어느 모델을 쓸지 고르는 갈림길이다.
  2. 정해진 일은 크기가 지시서에서 셀 수 있는 수로 거의 정해진다: 같은 지시서를 쪽 범위만 바꾼 p84–p88은 분이 ×1.3쯤만 흔들렸다.
  3. 찾는 일(버그 찾기·조사·설계부터)은 찾을 것의 수가 지시서에 없어 센 수로 못 잡는다(p45 '건드릴 자리가 정해졌나', H_settled_integration '찾을 것의 수가 분을 정한다').
  4. 2026-11-03 날짜순 시험의 뒤 45건이 거의 다 정해진 일이라(턴이 있는 38건 중 지문 분석 19·풀이지 일 15), 정해진 일 모델부터 바로 시험할 수 있다.
- **정해진 일 모델**: 턴 = 기본 몫 + Σ(센 수 × 하나마다 몫). 센 수는 읽을 것·만들 것·쓸 덩어리(절·단계)·고칠 곳·확인 — 지시서에 적힌 것만, 모르면 비움. 지금 스위치(본뜰 것이 있다·위치까지 적혀 있다·이어 보냄 등)는 하나마다 몫을 바꾸는 조건으로 남긴다.
- **찾는 일 모델**: 지시서에 상한(찾을 것 최대 N개·보고서 몇 줄까지·확인 바퀴 최대 M번)을 넣어 셀 수 있게 만들고, 상한을 못 두는 일만 "기본 몫 + 찾은 것마다 한 바퀴". 기록이 쌓이면 만든다. 그때까지는 손 예측과 빗댄 기록.
- **섞인 일**: 두 몫을 따로 계산해 더한다(지시서 읽기·둘러보기·보고 같은 기본 몫은 한 번만). 순수한 기록이 각 몫을 맞추고, 섞인 기록은 두 몫이 정말 더해지는지 시험한다(안 더해지면 서로 끼치는 조건을 찾는다).
- **섞인 일 보내기** (2026-11-03 사용자 결정): 지시서를 쓰는 메인이 같은 에이전트에 두 회차로 나눠 이어 보낸다 — 찾기 먼저, 고치기는 다음 회차(찾은 것 N개 → 고칠 곳 N개로 정해진 일이 된다). 다른 에이전트로 나누지 않는다(관련 작업은 한 에이전트, `docs/dispatch.md`). 두 부분이 얽혀 순서를 못 나누면 한 번에 보내고 두 몫의 합으로 계산한다. 사용자가 요청을 나눠 줄 필요는 없다.

  - 나눈 효과는 이번 시험으로 판단할 수 없다: 나눈 쪽은 맞출 기록이 적어 읽을 것 몫을 못 세웠고 절반이 '모름'이었다(안 나눈 쪽이 높은 것은 이 탓이 섞였다).
  - 짐작되는 까닭(검증 안 됨): 작업 설명은 지시서의 짧은 요약이라 수가 드물고 빠진다. 쓸 덩어리에 절·줄·라벨 칸이 섞여 1–1,350으로 벌어졌다(지시서에 '절·단계·항목·줄'을 같이 적은 탓). 기능·시스템 수를 넣을 칸이 없다(보고서).
  - 그래서 계산 조각으로 올리지 않는다. 크기 정보는 지금 '어느 지난 일과 비슷한가'(빗댄 기록 84 %)에 들어 있다. 다음 방향은 사용자와 정한다: (1) 앞으로 보낼 때 실제 지시서에서 세어 `size`에 적고 새 기록으로 다시 시험, (2) 빗댄 기록 고르기를 누구나 같은 답을 낼 기준으로 만들기.

## 보낼까 판단 (2026-11-03 사용자 결정)
감으로 두면 AI는 안 보내는 쪽으로 기운다(O_undersend): 보내는 비용은 바로 보이고, 직접 했을 때 메인 맥락이 커져 그 뒤 모든 응답에서 다시 읽히는 비용은 안 보인다. 2026-11-03 메인 세션은 맥락이 7.6만 → 80.6만 토큰으로 커졌고 다시 읽은 양이 1억 500만 토큰이었다(O_main_context_cost). 그래서 둘을 같은 단위로 놓는다 — 규칙 R_send_or_not.
- **계산** (`decide.py`, 숫자는 `decide.toml`): 직접 = T×(M+A/2) + A×L, 보냄 = S + K×M + R×L. T·S 일의 줄 수·토큰(손 예측이 있으면 그것 — 계산기보다 잘 맞는다 — 없으면 계산기), M 지금 메인 맥락(메인 대화 기록에서 읽음), A 직접 하면 늘어날 맥락 = 2×(S/T − base), L 남은 대화 줄 = 남은 응답 어림(기본 50) × 2, K 보내고 기록하는 메인 줄(묶음 명령으로 10), R 보내면 메인에 남는 보고(5천). 토큰은 기록 단위(줄마다 더한 값).
- **토큰 말고 고를 까닭** (`decide.why`): 새 눈(검토·점검 — 메인은 이미 닻이 내려 있다), 대화 계속(뒤에서 돌게 보내고 사용자와 이야기), 대화 맥락(대화에서 쌓인 판단이 많이 필요하면 직접), 결과를 가림. 비용만 까닭으로 들었는데 비용으로는 다른 쪽이 싸면 검사가 막는다.
- **기록**: 보낸 기록은 `[dispatch.decide]`(2026-11-04부터 필수, batman 제외), 직접 한 일은 `direct.toml`(문턱: 도구를 대여섯 번 넘게 쓸 일 — 기록이 없으면 검사할 대상이 없어 막지 못한다). 직접 한 일의 실측은 메인 대화 기록에서 `--rounds`로 그 요청의 시작·끝을 보고 `record finish <m…> <메인 기록> --after --until` — 메인 맥락이 실제로 늘어난 양(`added_k`)도 잰다.
- **시험** (`decide_cost`): 고른 쪽의 실제 비용(보냄 = 작업자 실측 + 메인 몫 추정, 직접 = 메인 실측 + 실제로 늘어난 맥락 × 남은 줄)이 다른 쪽 추정보다 작았나. 판단 기록 10건이 쌓이면 판정. 고르지 않은 쪽은 해 보지 않아 추정뿐이다. `decide.toml`의 숫자는 2026-11-03 세션에서 잰 값으로 처음 정했고 판단 기록이 쌓이면 손으로 다시 정한다.

## 빗댄 기록 규칙: 정해진 일은 가장 가까운 지난 일의 시간을 따른다 (2026-11-03 사용자 결정 — 시험 전에 적음)
크기 모델이 실패하고(위) 빗댄 기록에서 출발한 예측이 가장 잘 맞아서(시험 기록 84–86 %), AI가 감으로 고르던 빗댄 기록을 누구나 같은 기록을 고르는 규칙으로 바꾼다. AI는 지시서를 보고 정해진 질문(상태)에 답만 하고, 고르기는 기계가 한다. 난이도 같은 점수 칸은 두지 않는다 — 크기는 고른 기록의 실제 시간에 들어 있다.
- **구조**: 할 일이 정해진 일(S_specified = 예) → 아래 규칙으로 지난 기록을 고른다 → 그 기록들의 실제 분 → × 범위 → 분 범위 → 가운데 값의 구간으로 말한다(R_say_numbers_v3). 찾는 일·섞인 일은 지금은 손 예측(나중에 따로).
- **쓸 수 있는 후보**: 보낼 때 이미 끝나 있던 기록만 — 날짜가 앞서거나, 같은 날이면 끝 시각이 이 기록의 시작 시각보다 앞(기록 글의 'HH:MM:SS → HH:MM:SS'), 시각을 모르면 다른 배치만.
- **반드시 같은 답**: S_specified, S_other_model, S_resumed, S_web, S_fixed_input, S_cloud_session('모름'은 다른 답으로 친다). 일의 큰 모양과 모델·회차가 다르면 시간이 다른 세상이다.
- **우선순위**: 같은 저장소 → S_template_given·S_render·S_no_code·S_fix_existing·S_research·S_spec_fixed 중 같은 답이 많은 것. 맨 앞이 동점이면 **동점 묶음의 실제 분의 가운데 값**(사용자 제안 '기댓값' — 같은 것이 여럿이면 하나를 고르지 않고 가운데를 쓴다).

## 따라 할 방식 — 사용자가 자기 논리집을 쌓은 방식 (출처: docs/knowledge-format-v0.md 3절, docs/pieces-v0.md, 2026-10-14 대화)
1. **빠진 고리를 묻는다.** "반복한다고 왜 점수를 매기나, 최근은 갑자기 어디서 나왔나" → 목표와 이유가 없는 규칙은 채운다. 지금 살아 있는 규칙 중 이유가 "기록 없음"인 것은 없다(테스트가 막는다).
2. **실패하면 예외인지 개정인지 가른다.** "예외가 아니라 논리를 수정해야 하는 거 아닐까?"
   - 자주 일어나고 이유 안의 가정이 틀렸으면 → 새 버전.
   - 이유는 맞는데 드문 바깥 상황이면 → 예외.
3. **예외는 원래 전제에 있어야 했던 조건으로 본다.** "애초 전제에 '시험 기간이다'가 있어야 했던 거 아니야?" → 자주 걸리면 조건으로 올리거나 규칙을 둘로 나눈다. 예: R_tok_long → 짓기/고치기로 나눈 v5, R_other_models_v3 → 작업 모양별 셋.
4. **확인 안 된 건 가설로 둔다.** "확인되지 않은 가설이니까" → 규칙도 늘 가설이다(`status = "hypothesis"`). 시험을 통과해도 상태는 그대로이고, 성적표에 성적이 쌓인다(2026-10-19, Lean 방향: 모든 주장에 시험 기록).
5. **부작용을 보면 숨은 목표를 찾고, 대가로 받아들일지 정한다.** 받아들인 기록이 없으면 `audit`이 잡는다(H_turns_over는 낳는 규칙 v1이 물려 지난 일로 본다).
6. **사용 습관과 능력을 구분한다.** "Flash는 거의 병렬 작업용으로만 썼다" → 규칙의 근거가 쓰던 범위에서만 나왔는지 본다. 예: R_doc_work의 근거는 설계부터 한 글 한 건뿐이었다. Sonnet은 비교 라운드에만 써서 도구 작업 근거가 한 건(d42)이다.
7. **판정한 이유를 원리로 만든다.** 질문 1의 "개수의 차이" → 돌아보기의 이유를 가설로 올린다(예: "찾을 것의 수가 분을 정한다" → H_settled_integration).
