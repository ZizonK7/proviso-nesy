# 지식 양식 초안 v0 — 층위 + 조건 단어장 (분야 A)

- 작성: 2026-10-14, Claude. 사용자 피드백 반영 전 초안.
- 관련: [rule-drafts-v0.md](rule-drafts-v0.md) (손으로 쓴 규칙), 원안 2.1절(규칙 5요소)

## 1. 정보 층위

| 층위 | 무엇 | 예 | 바뀌는 방식 |
|---|---|---|---|
| **사실 (FACT)** | 지금 세상이 어떤 상태인가 | "Sol 모델은 현재 계정에서 쓸 수 있다: 아니오" | 시간이 지나면 낡음. **확인 시점**과 **출처**를 붙이고, 새로 확인되면 덮어씀(이력은 보존) |
| **규칙 (RULE)** | 이런 조건에서 이렇게 하면 보통 이렇게 된다, 단 예외 | 원안의 P/W/C/R/ω | 결과 피드백으로 신뢰도가 오르내리고, 실패에서 예외가 추가됨 |
| **선호 (PREFERENCE)** — 제안 | 사용자가 원하는 것 | "본문은 맞춤법만 고치게", "모델은 바꾸지 말 것" | 사용자가 말할 때만 바뀜. 맞고 틀림이 없음 |

- 규칙의 조건은 사실을 참조할 수 있다. 예: `조건: 모델.Sol.사용가능 = 예`. 사실이 바뀌면 그 사실에 기대는 규칙의 발동 여부가 자동으로 바뀐다 → 규칙 자체를 고칠 필요 없음.
- 선호 층은 ai_company의 사용자 결정 4건(맞춤법만 수정, 모델 유지 등)을 보고 제안. 사실도 규칙도 아니라서 따로 두는 게 맞아 보임.

### 사실 예
```yaml
id: F_001
내용: 모델.Sol.사용가능 = 아니오
확인시점: 2026-09-28
출처: 실행 기록 (실패 5건: 13249802, 69537787, d1b6ece4, bc513069, 3a345f52)
---
id: F_001   # 같은 사실의 새 값, 이전 값은 이력으로
내용: 모델.Sol.사용가능 = 예 (gpt-6-sol, 대체 경로)
확인시점: 2026-10-06
출처: ai_company README 검증 기록
```

## 2. 조건 단어장 (분야 A: AI에게 소프트웨어 작업 맡기기)

규칙의 조건·방법·결과는 아래 단어로만 쓴다. 모든 값은 **모름**을 가질 수 있다(3값).
"알아내는 법"이 `자동`이면 기록·코드에서 기계가 바로 읽고, `판단`이면 로컬 모델이 추정하거나 사용자에게 묻는다.

### 작업 (무슨 일인가)
| 단어 | 값 | 알아내는 법 |
|---|---|---|
| 작업.종류 | 구현 / 테스트작성 / 설계 / 분석·조사 / 코드리뷰 / 디버깅 | 자동 (ai_company `work_role`) |
| 작업.수정파일수 | 숫자 | 자동 (최종 diff) |
| 작업.저장구조의존 | 예 / 아니오 — DB 경로·필드 이름·단위 같은 기존 데이터 구조에 기대는가 | 판단 |
| 작업.순수기능 | 예 / 아니오 — 입력→출력만 있고 바깥 상태를 안 건드리는가 | 판단 (일부 자동 가능) |
| 작업.설계확정 | 예 / 아니오 — 승인된 설계나 함수 모양이 이미 있는가 | 자동 (선행 설계 요청 존재 여부) |
| 작업.병렬조각 | 예 / 아니오 — 다른 작업자와 동시에 진행되는 조각인가 | 자동 (같은 요청 안 실행 시각 겹침) |

### 맡긴 방식 (어떻게 시켰나)
| 단어 | 값 | 알아내는 법 |
|---|---|---|
| 맡김.작업자 | Flash / Opus / Sol / Astra / 총괄직접 | 자동 |
| 맡김.저장소접근 | 예 / 아니오 — 작업자가 실제 코드를 직접 볼 수 있었나 | 자동 (ai_company 작업자는 항상 아니오) |
| 맡김.계약전달 | 원문 / 요약 / 없음 — 경로·필드·단위를 어떻게 넘겼나 | 판단 (프롬프트 확인) |
| 맡김.목표명시 | 예 / 아니오 — 사용자의 1순위 목표를 프롬프트 앞에 적었나 | 판단 |
| 맡김.선택이유 | 자유 문장 — 왜 이 작업자·방법을 골랐나 | 자동 (`routing_reason`) |

`맡김.선택이유`는 규칙 조건에 직접 쓰지 않는다. **선택 편향을 가려내는 용도**다(아래 3절).

### 결과 (어떻게 됐나)
| 단어 | 값 | 알아내는 법 |
|---|---|---|
| 결과.재작업 | 그대로 / 일부수정 / 대부분재작성 / 못씀 | 판단 (총괄 평가의 rework 항목에서 추정) |
| 결과.테스트 | 통과 / 실패 / 없음 | 자동 |
| 결과.사용자평가 | 잘됨 / 아쉬움 / 모름 + 이유 | 사용자 |

## 3. 사용자 피드백으로 바뀐 것: 규칙 1이 사라짐

v0의 규칙 1은 "Flash는 작고 얽히지 않은 작업에만"이었다. 사용자 지적:
> Flash는 거의 병렬 작업용으로만 썼다. "다른 코드와 얽히지 않음"은 병렬로 나누기 위한 조건이라 들어간 것.

즉 "얽히지 않음"은 **Flash의 능력에 대한 사실이 아니라 Flash를 그렇게만 썼다는 흔적**이다(선택 편향). Flash가 얽힌 작업을 못하는지는 이 데이터로 알 수 없다 — 비교 대상이 없다.

실패 사례를 다시 보면 공통 원인은 Flash가 아니라 **작업자가 실제 코드를 못 봤고 정확한 계약도 못 받았다**는 것:
- `3a345f52` 웹 모듈: Firestore 경로·단위를 추측 → 원문 계약을 주고 다시 맡기자 개선
- `cebed92d` 테스트: 실제 코드가 없으니 가짜 객체를 검사하는 테스트를 만듦

그래서 규칙 1을 폐기하고 규칙 2로 흡수:

```yaml
id: R_002
조건:  [맡김.저장소접근 = 아니오, 작업.저장구조의존 = 예]
방법:  [맡김.계약전달 = 원문]
결과:  [결과.재작업 ∈ {그대로, 일부수정}]
예외:  []
근거:  [3a345f52(실패→개선), cebed92d(실패)]
출처:  AI 판단 (총괄)
상태:  임시
메모:  Flash 고유 능력 차이인지는 미확인 — Flash가 병렬에만 쓰여 비교군 없음
```

```yaml
id: R_003
조건:  [작업.종류 ∈ {설계, 분석·조사}, 맡김.작업자 = Opus]
방법:  [맡김.목표명시 = 예]
결과:  [결과.재작업 = 일부수정]
예외:
  - 맡김.목표명시 = 아니오 → 우선순위 어긋남 (aeee9e94)
주의:  근거 없는 단정이 섞이는 경향 → 검수 필수 (d1b6ece4, 85a6e9c9)
출처:  AI 판단 (총괄)
상태:  임시
```

`주의`는 원안 5요소에 없는 칸이다. "예외(이럴 땐 규칙이 안 통함)"와 달리 "규칙은 통하지만 따라오는 부작용". 툴민 원 모델의 **한정어(Qualifier)** 에 가깝다. 넣을지 결정 필요.

## 3-1. 사용자 검토 결과 (2026-10-14)

작업 5건을 보여주고 "잘됨/아쉬움"을 물었더니:
- 사용자는 **실사용 경험**으로만 판단할 수 있다. 과정(테스트가 가짜였다, 경로를 추측했다)은 사용자 눈에 안 보이고, 실사용에서 문제가 없었으면 "뭐하는 거지?"가 됨.
- **AI 판단과 사용자 판단이 갈린 실제 사례**: Flowlog 제목 추천(`5038da80`/`9033f69c`). AI 평가는 전 항목 positive. 사용자 실사용: "새로 한 번 쓴 제목이 바로 1등으로 올라온다. 마지막 칸(5번째) 정도로 들어오길 바랐다." 원래 요청(`bc513069`)도 "새 항목 하나가 안 쓰는 옛 추천 하나를 대체"였음 → 요구와 구현이 어긋났는데 AI 검수는 못 잡음. **사용자 평가를 AI 평가보다 높게 쳐야 하는 근거.**
- 규칙 3의 근거(`aeee9e94`, "Opus가 사용자 목표를 뒤로 밀었다")는 총괄이 해석한 사용자 목표에 기대고 있음. 기록된 목표: "모르는 분야를 AI와 대화하고, 문제를 정의하고, AI가 의도대로 했는지 확인할 수 있을 정도로 배우기(학문적 완전 습득 아님)". 사용자 반응: 처음엔 "그냥 학습 AI 아니야?" → 기록된 목표 문장을 보여주자 "내 의도와 맞다, 내가 그렇게 하라고 했다" → **R_003의 예외 근거 유효.**
- 그래프 시각화 예시: https://claude.ai/artifact/1gPrvy1BFyk4TkgLVdsCHD (R_002·R_003·사실 1개 + Flowlog 추천 사슬 R_P1→R_P2)
- 사용자 의견: 코딩 과정 논리는 본인이 잘 몰라서 만들 필요가 있는지 의문. → 과정 규칙(R_002, R_003)은 AI만 판단 가능 = "사용자 검증" 원칙과 안 맞음. 분야 A 재검토 중.

## 3-2. 규칙에 "목표"와 "이유" 칸 추가 (2026-10-14, 사용자 지적)

그래프에서 "같은 종류 기록을 반복한다 → 최근+빈도로 점수" 를 보고 사용자가 지적: "반복한다고 왜 점수를 매기나, 최근은 갑자기 어디서 나왔나". 빠진 고리가 둘:
- **목표** (왜 이걸 하나): "제목을 빨리 고른다"
- **이유** (왜 이 방법이 통한다고 믿나): "다음에 쓸 제목은 자주·최근 쓴 것일 가능성이 크다". 그리고 "최근" 정보의 출처인 조건("횟수·마지막 날짜가 저장돼 있음")도 빠져 있었음.

규칙 칸 = **목표 / 조건 / 방법 / 이유 / 결과 / 예외** (+ 주의, 신뢰도, 근거, 출처, 상태).
- 원안의 W(Warrant)를 "방법"으로만 읽었던 게 문제. 툴민의 Warrant는 원래 "왜 전제에서 결론으로 갈 수 있나"(= 이유)다. → W를 **방법**과 **이유**로 분리.
- **예외는 이유를 공격한다.** "한 번만 쓴 제목"은 "최근에 썼으니 또 쓴다"는 이유가 깨지는 경우 → 사용자 아쉬움과 정확히 일치. 이유 칸이 있어야 예외의 위치가 보이고, 부검(원안 4.3) 때 "어느 가정이 틀렸나"를 물을 수 있다.
- 목표는 그래프의 도착점. 추론 = 현재 상태에서 목표 칸까지 가는 길 찾기.

## 3-3. 예외 vs 규칙 고치기 (2026-10-14, 사용자 지적)

사용자: "예외로 적었던 것들도 예외가 아니라 사실은 논리를 수정해야 하는 거 아닐까?" → 맞았음. 적었던 두 개 모두 예외가 아니었다.
- Flowlog "한 번 쓴 제목이 바로 1등" → **규칙 고치기.** 흔한 상황이고, 규칙 안의 가정("최근 = 또 쓴다")이 틀렸고, 방법을 바꾸면 해결됨. R_P1 v1 → v2로 개정, 별도 규칙이던 R_P2는 v2에 흡수.
- R_003 "목표를 안 적으면 우선순위 어긋남" → **근거.** 규칙이 생겨난 실제 실패 기록일 뿐 예외가 아님.

구분 기준 (실패를 만났을 때):
| | 규칙 고치기 | 예외 붙이기 |
|---|---|---|
| 빈도 | 평소에도 자주 | 드물게 |
| 원인 | 규칙 안의 가정(이유)이 틀림 | 이유는 맞는데 규칙 바깥의 특수 상황 |
| 해결 | 방법을 바꾸면 해결 | 방법을 바꾸면 평소가 나빠짐 → 그 상황에서만 덜 믿음 |

- **원안의 빈틈:** 원안 4.3은 실패 시 예외 추가(R ← R ∪ {r_new})만 있고 규칙 본문을 고치는 연산이 없다 → 예외가 덧대어지기만 함. **학습 연산에 "규칙 개정(새 버전)"을 추가.** 이전 버전은 삭제하지 않고 보존(무엇이 왜 바뀌었는지 근거와 함께).
- 부검(원안의 사후 분석)은 "이유가 틀렸나(→ 개정) / 특수 상황인가(→ 예외)"를 먼저 묻고, 판정은 사용자 확인.
- 논리적으로 예외는 "조건에 '이 상황이 아님'을 붙인 것"과 같다. 그래도 따로 두는 이유: 조건은 참임을 확인해야 규칙을 쓰지만, 예외는 해당한다는 증거가 없으면 없다고 보고 규칙을 쓴다(모르면 질문). 이 차이 때문에 칸을 분리.
- 규칙 칸에 **근거**, **버전** 추가.

## 3-4. 예외 = 나중에 발견된 조건 / 선호 층 재검토 (2026-10-14)

- 사용자: "그러면 애초 전제에 '시험 기간이다'가 있어야 했던 거 아니야?" → 논리적으로 예외 = "~가 아님" 조건. 따로 두는 이유: (1) 깨지는 상황은 미리 다 못 적고 실패 후에 발견됨 (2) 조건은 참을 확인해야 쓰지만 예외는 증거 없으면 "해당 없음"으로 보고 씀(모르면 질문). 자주 걸리는 예외는 정식 조건으로 승격하거나 규칙을 둘로 나눔. 예외 = 단서 조항(proviso), 프로젝트 이름의 유래.
- 사용자: "사실/선호로 나눌 필요가 있나? 둘 다 개인 경험인데." → 나눴던 기준은 관찰("써 보니 그렇다") vs 바람("이러면 좋겠다"). 그런데 "새 건 마지막 칸" 선호는 이유가 빠진 규칙이었음. 사용자가 밝힌 이유: "최근 활동이 추천에 너무 늦게 반영 → 같은 활동 반복 입력이 귀찮음 → 입력을 안 하게 됨. 새 활동 추가에 거부감이 없게 하려고 최근 것을 넣었다."
- 제안: **선호 층 폐지.** 사용자 바람은 **목표**이거나, 사용자 경험이 근거로 붙은 **방법**. 규칙은 전부 한 사람의 경험이므로 "개인적이냐"는 구분 기준이 아님. 유의미한 구분 = 확인 가능한 것(관찰·사실, 틀릴 수 있음) / 원하는 것(목표) / 하는 것(방법). — 사용자 확인 대기.
- Flowlog 추천 재구성(초안): 큰 목표 "기록을 꾸준히 한다" ← 목표 a "자주 하는 활동은 빨리 고른다"(방법: 자주 쓴 순 1~4칸) + 목표 b "새 활동도 부담 없이 추가한다"(방법: 처음 쓴 제목도 바로 5번째 칸, 근거: 위 사용자 경험). v1은 b를 과하게 챙겨 a를 해친 것 → 5번째 칸은 두 목표의 절충. **"왜 1등이 아니라 마지막 칸인가"는 내 추측(a 보호) — 사용자 확인 대기.**
- 목표끼리 위계가 생김(큰 목표 ← 하위 목표) → 그래프 도착점이 하나가 아니라 목표 나무.

**사용자 답 (같은 날):**
- 마지막 칸인 이유 확인: "한 번 썼다고 순위를 차지하는 건 명분이 없어서 마지막에 하나 정도만 넣는 거" → R_P1b 이유에 반영.
- "선호" 대신 **"가설"**: "내 개인적으로는 확인되지 않은 가설이니까." → 선호 층 폐지 확정. 보라 상자 = 가설(아직 확인 안 된 주장). 규칙에도 상태 배지(가설 → 검증됨). 원안 7장의 "임시 논리(Probationary)"와 같은 개념.
- **사용자가 그래프에서 새 가설을 추론함**: "한 가지 새 활동을 연속으로 하면 자연스레 4등 안으로 오르지만, 새 활동 2개 이상을 번갈아 하는 사람은 계속 직접 입력해야 한다. 다만 UI를 5개로 간결하게 한 대가라고 볼 수도." → 숨어 있던 **목표 c "화면은 간결하게"**가 드러남. 부작용(목표 b 일부 훼손)을 목표 c의 **대가로 수용**한 결정 → "결과·부작용" 칸과 "수용한 대가" 표시가 필요.
- 이 가설은 확인 가능: (1) 규칙대로 시뮬레이션 (2) 실제 Flowlog 기록에서 새 활동을 번갈아 쓴 빈도. **시스템이 자동으로 해야 할 일의 실례** — 사람이 그래프를 보고 한 추론(부작용 예측)을 엔진이 하게 만드는 것.
- 현재 Flowlog 구조: 큰 목표 "기록을 꾸준히" ← a(빨리 고르기) / b(새 활동 부담 없이) / c(화면 간결). R_P1a(1~4칸 여러 번 쓴 순) → a, R_P1b(5번째 칸 = 가장 최근 처음 쓴 제목 하나, 근거 = 사용자 관찰) → b, "5칸만" → c. v1은 둘로 나뉘며 개정.

## 4. 설계에 주는 교훈

- **"왜 그 방법을 골랐나"를 반드시 기록한다.** 안 그러면 사용 습관을 능력 차이로 잘못 배운다. 규칙 후보가 나오면 `선택이유`가 조건과 겹치는지 검사해서, 겹치면 "선택 편향 의심" 표시.
- 기록에서 **자동으로** 읽을 수 있는 단어와 **판단**이 필요한 단어를 나눠 두면, 판단 쪽만 로컬 모델/사용자 질문으로 보내면 된다.

## 5. 규칙·가설 통합 — "성적 붙은 가설" (2026-10-19, 사용자 결정)

사용자가 원하는 흐름:
1. 현상의 결과를 보고 가설을 세운다. 기존 논리에 잇는 것도 가설이다.
2. 쓸 때는 논리집대로 흘러간다.
3. 틀리면 논리의 **어디가** 틀렸는지 짚고, 그 조각을 **더 쪼개고** 그래프를 다시 잇는다.

사용자 생각: 논리 자체는 잘 안 틀린다. 틀리는 건 논리를 흐리게 잡았기 때문이다. 목표는 Lean처럼 — 모든 주장은 증명(시험) 기록을 달고, 틀리면 어느 단계가 틀렸는지 드러난다.

바뀐 것 (현재 칸 정의는 [proviso/CLAUDE.md](../proviso/CLAUDE.md)):
- **'검증됨'(verified) 상태를 없앴다.** 규칙은 "방법이 붙은 가설"이다. 상태는 `hypothesis`(지금 것)와 `retired`(이전 버전, 보존) 둘. 3-4절의 "규칙에도 상태 배지(가설 → 검증됨)"를 대신한다. 이유: 한 번 올린 배지는 그 뒤 성적이 떨어져도 그대로 남는다(agent_usage에서 '검증됨' R_time_turns_v2의 주장 성적은 44/54인데, 그 규칙을 쓴 예측의 분 범위 적중은 30/61이었다).
- **모든 가설에 성적표.** 엔진(`check`)이 (i) 자동 검사(분야 검사 함수, 세운 뒤 기록만)와 (ii) 판정 기록 `[[judgment]]`(사용자 실사용 / 실제 기록 재생 / 실측 / 자동 확인 / 시뮬레이션 / AI 판단)를 출처별로 보여 준다. 사용자 실사용이 가장 무겁다(3-1절). 예전 '검증됨'의 근거는 판정 기록으로 옮겼다(flowlog R_P1a: v1 실사용 '좋다' + 실제 기록 재생 98%).
- **시험 수단 없음**은 audit 경고. 자동 검사도 판정도 없는 가설은 아직 아무도 시험할 수 없는 주장이다. 못 붙이는 까닭이나 계획은 `test_plan`에 적는다.
- **틀리면 쪼갠다.** 새 버전이 이전 버전에 없던 조건(상태 노드)을 하나도 더하지 않으면 audit이 "쪼개지 않은 개정"으로 경고한다(숫자만 바뀜·합침·조건을 뺌 표시). 3-3절의 개정/예외 구분에 "조건 흐림 → 쪼갠다"가 더해져 셋이 된다:

| 틀린 까닭 (`review.why`) | 처리 |
|---|---|
| 조건 흐림 | 조건(상태)을 더해 쪼갠다. 새 버전의 `conditions`에 더한 상태가 보여야 한다 |
| 이유 틀림 | 새 버전 (3-3절 "규칙 고치기") |
| 바깥 상황 | 예외 (3-4절, 나중에 발견된 조건) |

- **돌아보기에 틀린 조각 칸**(agent_usage `dispatches.toml`): `review.wrong`(틀린 조각 id)과 `review.why`(위 셋 중 하나). 시간 구간이 빗나간 기록부터 필수(p04 이후). 지난 기록은 손으로 되짚지 않고, 분이 빗나간 기록이 턴 수(양) 탓인지 분당 턴(속도) 탓인지를 엔진이 계산해 보여 준다.

원안 대비: 원안 4.3절은 실패 시 예외를 더하는 연산만 있었고(3-3절에서 개정을 더함), 원안 한계 절(7장)의 임시 논리(Probationary Logic)는 일정 횟수(k회) 이상 실전 성공을 거두면 격리를 벗는다. 여기서는 올라가는 단계가 없다 — 모든 논리가 계속 성적을 받고, 성적표가 지금 얼마나 믿을 만한지를 보여 준다.
