## 규칙 1. Flash에게 맡길 수 있는 범위

| | |
|---|---|
| **조건** | 작업이 작고, 다른 코드와 얽히지 않은 순수 기능(입력 → 출력)이며, 승인된 설계와 함수 모양(API)이 이미 정해져 있음 |
| **방법** | Flash에게 구현과 테스트를 같이 맡긴다 |
| **결과** | 결과물을 거의 그대로 쓸 수 있다 |
| **단, 예외** | 여러 모듈이나 저장소 구조(DB 경로, 단위 등)에 얽힌 작업이면 → 추측으로 채우고, 실제 코드를 쓰지 않는 가짜 테스트를 만들어서 총괄이 대부분 다시 써야 했다 |

근거
- 잘됨: `9033f69c` 활동 제목 점수 계산기(순수 Kotlin 함수) — 구현·테스트 모두 positive, 16개 테스트 통과
- 예외 발동: `cebed92d` 테스트가 "가짜 객체가 가짜 값을 돌려주는지"만 확인(동어반복) → 교체 / UI 초안 대폭 재작성
- 예외 발동: `3a345f52` Firestore 경로·시간 단위를 추측, 테스트가 실제 코드 대신 복사한 장난감 검증기를 검사 → 6개 항목 전부 negative
- 중간: `13249802`, `7ebadc66` 범위가 좁은 UI 작업 — 쓸 만하지만 총괄 수정 필요(neutral)

## 규칙 2. 작업자가 저장소를 못 볼 때는 정확한 계약을 원문 그대로 준다

| | |
|---|---|
| **조건** | 기존 데이터 구조(경로, 필드 이름, 단위)에 의존하는 작업 + 작업자가 저장소를 직접 볼 수 없음 |
| **방법** | 경로·필드·단위를 요약하지 말고 원문 그대로 프롬프트에 넣는다 |
| **결과** | 추측으로 인한 오류가 줄어든다 |
| **단, 예외** | (아직 발견 안 됨) |

근거
- 실패 → 보완: `3a345f52` 첫 시도에서 경로·단위를 추측(전부 negative) → 같은 작업을 "추측 말고 정확한 저장소 계약"으로 다시 맡김 → negative에서 neutral로 개선
- 같은 원인: `b3fb4f19` Opus 설계도 "저장소 접근이 없어서" 기존 구조에 맞추는 수정이 필요했음

> 규칙 1의 예외를 규칙 2가 일부 메워 준다. 규칙끼리 이어지는 예.

## 규칙 3. 설계·분석을 Opus에게 맡길 때는 사용자의 1순위 목표를 맨 앞에 박아 둔다

| | |
|---|---|
| **조건** | 설계나 분석 문서 작업, 작업자는 Opus |
| **방법** | 맡기되, 사용자가 말한 가장 중요한 목표를 프롬프트 맨 앞에 명시한다 |
| **결과** | 구조와 원인 분석은 채택할 만하다 |
| **단, 예외** | ① 목표를 명시하지 않으면 우선순위를 엉뚱하게 잡는다 ② 근거 없는 단정("이 방식이면 품질이 보장된다" 등)이 섞인다 → 총괄이 걸러내야 함 |

근거
- 예외 ① 발견: `aeee9e94` 사용자의 핵심 목표(AI 활용 능력)를 2순위로 밀어 둠
- 예외 ① 반영 후: `3ba0d847` 다음 요청에서 "사용자 목표를 먼저 고정"하고 맡김 → 적용성 positive로 개선
- 예외 ②: `d1b6ece4`(근거 없는 품질 보장), `85a6e9c9`(근거 없는 집중도 추론, 실패 원인 = 모델)

> 실패에서 예외를 배우고 → 다음엔 방법을 고쳐서 → 결과가 나아진 흐름이 이미 기록에 있다. SELA가 자동으로 하려는 일의 실제 예.

## 써 보면서 드러난 질문

1. **판단 기준이 섞여 있다.** 평가 6항목(요구사항·정확성·적용성·재작업·정직성·효율)이 있지만 "잘됐다"의 기준은 결국 "총괄이 얼마나 고쳐야 했나"에 가깝다. 규칙의 "결과"를 무엇으로 잴지 정해야 한다.
2. **조건의 단어가 아직 애매하다.** "작고 얽히지 않은"을 기계가 판정하려면 "파일 1개", "외부 저장소 의존 없음" 같은 구체적 기준이 필요하다.
3. **환경 사실(규칙 4)을 어떻게 다룰까.** 유효 기간을 붙일지, 별도 저장소로 뺄지.
4. 근거가 1~3건뿐이다. 사용자 확인을 받으면 출처가 "사용자"로 올라간다.
